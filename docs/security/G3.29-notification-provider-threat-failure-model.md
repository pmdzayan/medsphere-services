# G3.29 Notification Provider Threat and Failure Model

## Scope

This model governs the provider activation boundary only. No real provider, credential, endpoint, SDK, webhook, or outbound notification is activated by G3.29.

## Authority boundary

Tenant authority is established before provider selection by MedSphere's authenticated and tenant-scoped workflow. Provider configuration, provider responses, destination data, acknowledgement data, or vendor identifiers must never create or widen tenant authority.

## Sensitive-data boundary

Provider credentials are injected through runtime secret/configuration references. Credential values, destination addresses/tokens, composed message bodies, arbitrary provider payloads, and raw provider errors must not be persisted in domain events, queue metadata, operational evidence, metrics, health responses, or logs.

The provider call boundary may receive the minimum volatile destination/content needed by a later approved adapter. That data is process-memory-only for the call and is not provider activation metadata.

## Failure classes

- `TRANSIENT`: bounded failures for which the existing queue retry policy may retry, such as timeout, rate limiting, or temporary provider unavailability.
- `TERMINAL`: configuration, unsupported-channel, rejected-request, invalid-credential-reference, malformed-response, or other failures that must not be treated as a successful acknowledgement.
- Unknown/raw exceptions are normalized at the worker boundary to coded privacy-safe failure evidence; raw provider text is never evidence.

A later provider adapter must map vendor-specific errors into a bounded internal code plus one of these classes. It must not expose raw response bodies or destination data.

## Acknowledgement mapping

Provider acknowledgements are normalized to `ACCEPTED`, `REJECTED`, or `UNKNOWN`. Provider-specific acknowledgement values may be used transiently by an adapter but must not enter the queue/domain contract. A provider reference may cross the adapter boundary only as bounded volatile material and may be hashed before persistence; the raw value is not operational evidence.

## Idempotency

The existing notification delivery ID remains the logical idempotency key. Retries and duplicate worker execution must reuse it. Provider-generated identifiers never replace MedSphere's logical idempotency authority.

## Routing and fallback

Activation is explicit and channel-specific. G3.29 selects `EMAIL` as the first supported channel. Unsupported channels fail closed. A configured provider key must resolve to the exact matching adapter; no alternate provider or channel is selected silently.

## Timeout and circuit semantics

The activation contract permits only bounded network timeouts from 250 ms through 10 seconds, with 5 seconds as the default. A future adapter may implement circuit breaking, but an open circuit must surface as a coded unavailable/degraded condition and must not trigger silent fallback.

## Health and readiness

Provider capability state is represented independently as `DISABLED`, `READY`, `DEGRADED`, or `UNAVAILABLE`. Ordinary health/readiness must expose metadata only and must not send a notification or disclose credentials/destinations. Network probes require separate approval when a real provider is introduced.

## Threats and required controls

- Credential disclosure: secret references only; never log or persist values.
- Recipient disclosure: no destination/contact value in logs, metrics, health, attempt evidence, or domain events.
- Message disclosure: no composed body/subject in provider operational evidence or logs.
- Cross-tenant routing: provider data cannot establish tenant identity or authorize a route.
- Configuration downgrade: invalid, ambiguous, incomplete, or conflicting activation fails closed.
- Silent fallback: exact channel/provider match required; no alternate provider selection.
- Duplicate delivery: stable MedSphere delivery ID is the logical idempotency key.
- Provider payload injection: vendor response/error payloads are normalized to bounded internal codes.
- Unbounded hangs: adapters must obey the validated timeout bound.
- Misleading readiness: disabled/unavailable state is explicit; no fake success state for external delivery.

## Explicit prohibitions

G3.29 does not approve production provider activation, real external delivery, real healthcare data, credential provisioning, inbound delivery receipts, vendor webhooks, Maps, FHIR, ABDM, billing, returns, recall, Blood Bank, analytics expansion, or unrelated frontend work.
