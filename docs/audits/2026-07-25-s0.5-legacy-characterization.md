| ---------------------------- | ---------------------------------------- | ------------------------- | ----------------------------- |

| `Inventory.reservedQuantity` | `inventory.repository.ts` update         | Yes                       | Root client (not transaction) |
| `Batch.currentQuantity`      | `batch.repository.ts` update             | Yes                       | Root client (not transaction) |
| `StockMovement` quantity     | `stock-movement.repository.ts` create    | Mutable (has `deletedAt`) | Root client (not transaction) |
| `InventoryHistory` quantity  | `inventory-history.repository.ts` create | Mutable (has no trigger)  | Root client (not transaction) |

**Conclusion:** There are 5 mutable quantity authorities with no single source of truth. ADR-005 reduces this to 1 (Batch).

## Apparent vs real transaction boundaries

- `$transaction` is called with a callback
- Mocks execute the callback synchronously (`(cb) => cb()`)
- Repository methods use `this.prisma.client` (root client), NOT the transaction client argument
- Therefore, the mock cannot distinguish whether the transaction client is passed
- In production, root-client repository calls inside `$transaction` can commit partial writes

**Evidence:** The existing `stock-movement.service.spec.ts` mock at line 125:

```typescript
$transaction: jest.fn((cb: () => Promise<unknown>) => cb()),
```

This executes the callback but does NOT verify the callback receives the transaction client.

## Identity and tenant sources

| Service                          | Identity source                                     | Issue                                    |
| -------------------------------- | --------------------------------------------------- | ---------------------------------------- |
| reservation-service controller   | Hard-coded `'00000000-0000-0000-0000-000000000000'` | No tenant; no authenticated user         |
| inventory-service reservation    | `userId` parameter from caller                      | No tenant-scoped verification            |
| inventory-service stock-movement | `dto.userId` from caller                            | No tenant-scoped verification            |
| Generic Reservation model        | No `tenantId` field                                 | Cross-tenant data isolation not enforced |

**Conclusion:** No tenant authority exists in any reservation or stock operation. ADR-005 requires tenant scope on every row.

## Retirement trigger

Every new characterization test should be retired when its corresponding ADR-005 implementation is accepted and the legacy behavior is replaced.

The tests are labeled with `— legacy characterization` in their `describe` blocks for easy identification in test output. Do not delete tests before the replacement behavior is proven by CI.

## Decision

No inventory, batch, stock-movement, or reservation behavior documented here is production-approved. These tests exist solely to prove what unsafe behavior currently exists before the CTO replaces the persistence model during S0.5.
