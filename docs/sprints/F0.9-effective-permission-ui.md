# F0.9 Sprint Report: Effective-Permission-Aware Access UI

**Status:** Implemented and locally verified on `cto/frontend-foundation`

**Dependency:** F0.8 role lifecycle and membership access; accepted S0.3 trusted
authentication and S0.4 tenant-safe authorization

## Objective

Prevent the authenticated Team and Access workspace from advertising controls
the active tenant membership cannot use. Resolve current effective permissions
from the existing database-backed authorization boundary, keep backend guards as
the enforcement authority, and add rendered interaction coverage for restricted
and privileged operators.

## Delivered

- Added `GET /authorization/effective-permissions` for the authenticated
  membership. The response is derived from the same active user, membership,
  tenant, role, and permission chain used by `PermissionsGuard`.
- Effective permissions remain out of JWTs and browser-supplied identity. The
  endpoint is protected by the global authentication guard and returns only the
  caller's reviewed permission keys.
- The frontend BFF validates the effective-permission vocabulary before using
  it and requests role or permission catalogues only when the caller can read
  them.
- The Team workspace omits role creation, update, deletion, membership reads,
  and assignment mutations when their required permissions are unavailable.
- Role management supports update-only and delete-only operators without
  exposing the other mutation.
- Assignment readers receive a read-only view. Assignment checkboxes exist only
  for memberships with both assignment-management and role-read capability.
- Backend permission guards remain authoritative for every mutation. Frontend
  visibility is a usability and least-privilege improvement, not an
  authorization substitute.
- Vitest now uses the automatic JSX runtime used by the production Next.js
  application, allowing rendered component interaction tests without obsolete
  React imports.

## API contract

| Method | Route                                  | Authorization boundary                |
| ------ | -------------------------------------- | ------------------------------------- |
| `GET`  | `/authorization/effective-permissions` | Authenticated active membership, self |
| `GET`  | `/api/authorization/catalogue`         | HTTP-only access credential BFF       |

The response shape is `{ permissionKeys: string[] }`. Values must belong to the
accepted S0.4 permission catalogue. Unknown or duplicate values fail the
frontend boundary closed.

## Security and tenant behavior

- No tenant, membership, role, or permission authority is accepted from the
  browser.
- The trusted identity is produced by the accepted global authentication guard.
- The repository query proves the active user-membership-tenant relationship
  and excludes deleted roles.
- Permission discovery is intentionally self-scoped and does not require a
  separate permission that would make least-privilege discovery impossible.
- No database schema or migration change is required.
- Permission reads do not write durable audit events. Existing mutation and
  denial audit behavior is unchanged.
