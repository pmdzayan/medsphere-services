# F0.7 Sprint Report: Authenticated Team and Access Frontend

**Status:** Implemented and locally verified on `cto/frontend-foundation`

**Dependency:** Accepted S0.3 authentication and S0.4 tenant-safe authorization

## Objective

Replace the preview-only authenticated shell with a real session boundary and
deliver the first frontend workflow backed by accepted tenant APIs. The
workflow must remain fail-closed, must not expose bearer or refresh
credentials, and must not imply that unmounted backend modules are live.

## Delivered

- Platform routes require a valid, tamper-evident session profile paired with
  the HTTP-only rotating refresh credential.
- Login redirects into the authenticated workspace and stores no credentials
  in browser JavaScript.
- Single-use refresh credentials rotate through a same-origin backend-for-
  frontend route; failed refresh clears local session cookies.
- Sign-out attempts upstream revocation and always clears local credentials.
- The application shell displays the authenticated user and tenant context
  instead of invented organization and operator data.
- Navigation entries without accepted HTTP contracts are visibly unavailable
  and cannot lead to dead routes.
- `/team` loads the tenant role registry and migration-owned permission
  catalogue from accepted S0.4 APIs.
- Authorized operators can create bounded custom roles from the live
  permission catalogue. Backend authorization and durable audit remain the
  source of truth.
- Loading, empty, expired-session, permission-denied, upstream-unavailable,
  conflict, and malformed-response states are bounded and explicit.

## Security boundary

- Access and refresh credentials remain in `HttpOnly` cookies.
- Non-sensitive display context is integrity-protected with the current
  rotating refresh credential and is never used to authorize an operation.
- Mutation routes require a matching browser `Origin`.
- The backend derives tenant scope from the verified membership-bound access
  token; the frontend never accepts a tenant identifier for role operations.
- Upstream server errors and transport details are replaced with bounded public
  messages.
- Role creation still requires `authorization.roles.create`; catalogue reads
  require the accepted read permissions.

## Accepted frontend routes

| Route                          | Purpose                                  |
| ------------------------------ | ---------------------------------------- |
| `/login`                       | Establish membership-bound session       |
| `/dashboard`                   | Authenticated operations preview         |
| `/inventory`                   | Clearly labelled preview workspace       |
| `/team`                        | Live tenant role and permission workflow |
| `/api/auth/login`              | Credential-isolating login BFF           |
| `/api/auth/refresh`            | Same-origin credential rotation          |
| `/api/auth/logout`             | Session revocation and cookie cleanup    |
| `/api/authorization/catalogue` | Validated roles and permissions BFF      |
| `/api/authorization/roles`     | Same-origin custom-role mutation BFF     |

Reservations, billing, documents, and settings remain unavailable until their
accepted backend contracts exist.
