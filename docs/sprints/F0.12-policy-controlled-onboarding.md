# F0.12 Sprint Report: Policy-Controlled Tenant Onboarding

**Status:** Implemented and locally verified on `cto/frontend-foundation`

**Dependency:** F0.11 personal settings and the mounted S0.3 public
registration contract

## Objective

Complete the missing public onboarding experience using only the accepted
policy-controlled registration boundary. Provide a premium responsive form,
strict client and BFF validation, enumeration-resistant confirmation, bounded
errors, and clear language that a request is not an active account or tenant
membership.

## Contract audit decision

The S0.5 inventory application still exposes no accepted production HTTP
controller, so the inventory preview cannot honestly become live frontend work.
The mounted authentication application does expose one accepted frontend gap:

| Method | Backend route    | Frontend BFF route   |
| ------ | ---------------- | -------------------- |
| `POST` | `/auth/register` | `/api/auth/register` |

This endpoint resolves a normalized tenant slug, permits persistence only when
that tenant is active and explicitly enables self-registration, creates a
pending user and pending membership, and returns one generic public response.

## Delivered

- Added the public `/register` route with responsive Emerald Intelligence
  presentation and direct links from the landing and sign-in pages.
- Added first name, last name, organization slug, work email, password,
  confirmation, password visibility, pending, field-error, service-error, and
  success states.
- Normalizes the tenant locator, email, and names while preserving the password
  exactly as entered.
- Sends only the five accepted registration fields. Confirmation passwords and
  all UI-only state remain in the browser.
- Rejects unknown fields, client-supplied tenant or identity identifiers,
  malformed values, cross-origin requests, and malformed successful upstream
  responses before they can become trusted application state.
- Preserves the accepted generic response so the frontend cannot reveal
  whether a tenant, email, user, or membership already exists.
- Maps rate limiting and upstream failures to bounded public errors without
  exposing infrastructure details.
- Uses `Cache-Control: no-store` for every BFF response and never returns or
  stores a password or authenticated session.

## Security and privacy boundary

- The public request accepts a tenant slug only as a locator. The backend owns
  tenant resolution and registration policy; the client cannot provide a
  tenant ID, user ID, membership ID, role, permission, status, or activation
  decision.
- A successful response means only that the request was processed. It does not
  prove that an account or tenant exists and does not grant access.
- Registration is rate-limited by the accepted backend contract.
- No patient, employee-record, clinical, prescription, medicine, or payment
  data is introduced.
- No database schema, migration, backend controller, or backend business rule
  changes are required.
