# G3.23 — Notification Delivery Foundation

**Status:** Candidate; implementation and exact-head CI require review

**Repository baseline:** `9925df97e10c1c02a41e69489f285075437a84db`

**Accepted implementation source:** `3e7a8c04d8bb7cf60dfc726ec1ec0879cf1ff5c2`

**Architecture authority:** ADR-001, ADR-003, ADR-004, ADR-006, ADR-008,
ADR-013, ADR-014, and proposed ADR-015

## Objective

Create the provider-neutral, tenant-safe, durable notification-delivery
foundation required before any reservation, expiry, quarantine, blood-request,
or operational notification workflow is implemented.

## Five bounded work items

1. Provider-neutral notification contract and domain validation.
2. Tenant-safe recipient and routing boundary.
3. Delivery worker and provider adapter abstraction.
4. Idempotency, retry, failure/dead-letter handling, and delivery evidence.
5. Operational security, observability, and read-only admin boundary.

## In scope

- tenant-scoped durable delivery and append-only attempt evidence;
- opaque recipient references with transient destination resolution;
- `EMAIL`, `SMS`, `WHATSAPP`, and `PUSH` channel contracts without a selected
  provider;
- bounded template references and privacy-validated variables;
- leased claims, stable idempotency keys, coded outcomes, retries, and dead
  letters;
- injectable recipient resolver, provider adapter, and safe observer contracts;
- tenant-scoped metadata-only operational reads; and
- unit and PostgreSQL integration coverage for isolation, concurrency,
  idempotency, lease loss, retry, dead-letter, and evidence immutability.

## Explicitly out of scope

- real recipients, patient/contact lookup, preferences, consent, quiet hours,
  escalation, or routing policy;
- email, SMS, WhatsApp, push, or any other provider implementation or credential;
- rendered message bodies, template administration, localization, attachments,
  or clinical content;
- a reservation, expiry, quarantine, blood-bank, or other live workflow;
- replay/requeue mutation, provider webhooks, public APIs, frontend, broker, or
  separate notification-service deployment;
- Maps, location, FHIR, ABDM, analytics, payments, or production approval.

## Acceptance criteria

1. Duplicate source/workflow/recipient/channel enqueue is a no-op.
2. Cross-tenant source-event and delivery references fail at the database
   boundary.
3. Overlapping workers claim each eligible delivery once per lease window.
4. Provider calls occur outside database transactions and use a stable
   idempotency key.
5. A stale lease cannot record an outcome.
6. Retry timing is bounded and maximum attempts produce a dead letter.
7. Every terminal attempt creates immutable, coded evidence without raw errors,
   destinations, variables, or provider payloads.
8. Operational reads are bounded, tenant-scoped, and metadata-only.
9. Formatting, lint, tests, build, clean migration, drift, and supported upgrade
   checks pass at the exact published head.

## Completion meaning

Passing this sprint proves only a safe notification-delivery subsystem. It does
not prove that any user will receive a notification. The first bounded workflow
must be implemented separately using accepted G3.22 events.
