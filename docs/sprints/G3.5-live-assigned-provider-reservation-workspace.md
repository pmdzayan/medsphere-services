# G3.5 Sprint Contract: Live Assigned-Provider Reservation Workspace

**Status:** Implemented; exact-commit acceptance required

**Accepted base:** `7b2eb7821b27d212a6aebdb96610d81dd08832f1`

## Objective

Mount a read-only reservation workspace using the already accepted
assigned-provider reservation list contract without exposing lifecycle
mutations, patient identity, or adjacent payment and delivery scope.

## Accepted dependencies

- authenticated session context and the G3.4 assigned-provider BFF;
- `GET /inventory/providers/:providerId/reservations`;
- backend `inventory.reservations.read` permission enforcement;
- backend live membership-provider assignment enforcement;
- G3.3 reservation response and pagination semantics.

## Accepted scope

- reuse the active providers assigned to the authenticated membership;
- select one assigned provider and load its paginated reservations;
- filter by the accepted reservation status enum;
- display reservation ID, status, version, creation/expiry timestamps, total
  quantity, product identity fields, requested quantities, and batch allocation
  number/quantity/status;
- calculate only clearly labelled current-page counts from returned data;
- provide loading, empty, restricted, malformed-upstream, unavailable, retry,
  provider-selection, filter, and pagination states;
- enable the existing `/reservations` navigation item only when the route is
  mounted;
- keep successful and error responses non-cacheable.

## Explicitly blocked

- confirm, ready, complete, cancel, create, expire, or otherwise mutate a
  reservation;
- patient name, initials, contact details, prescription, clinical, pickup,
  payment, invoice, delivery, or controlled-medicine data;
- client-supplied user, membership, tenant, role, permission, or access-token
  authority;
- countdown, due-soon, priority, service-level, or operational-risk policy not
  present in the accepted response;
- changes to reservation persistence, lifecycle semantics, permissions, or
  accepted backend routes;
- treating the dashboard's fabricated reservation queue as live evidence.

## Same-origin BFF contract

| Method | Browser route                 | Accepted upstream route                           |
| ------ | ----------------------------- | ------------------------------------------------- |
| `GET`  | `/api/inventory/reservations` | `/inventory/providers/:providerId/reservations`   |
| `GET`  | `/api/inventory/providers`    | Existing accepted G3.4 assigned-provider boundary |

The reservation BFF accepts only `providerId`, `status`, `limit`, and `offset`.
Unknown query keys, duplicate scalar keys, invalid UUIDs, invalid enums, unsafe
integers, or out-of-range pagination fail before the upstream call. A
`providerId` selects a resource; it is never proof of access. The backend's live
assignment check remains authoritative.

## Response validation

The BFF rejects successful upstream payloads unless they have exact keys,
canonical UUIDs, accepted enums, bounded strings, valid ISO timestamps, safe
non-negative integer quantities, positive versions, and internally consistent
pagination.

For each reservation:

- `totalQuantity` must equal the sum of item `quantity` values;
- each item quantity must equal the sum of its allocation quantities;
- allocation status must be one of `HELD`, `CONSUMED`, or `RELEASED`;
- no unaccepted patient, prescription, price, payment, delivery, or internal
  persistence field may cross the boundary.

The BFF does not infer missing values or silently repair malformed upstream
data.

## Security and privacy behavior

- HTTP-only credentials remain server-side and are never returned to the
  browser.
- Browser-supplied tenant and membership identifiers are rejected and never
  forwarded.
- Backend `401`, `403`, and concealed `404` outcomes remain bounded.
- Successful and error responses use `Cache-Control: private, no-store`.
- The UI labels data read-only and renders no patient or prescription identity.

## Completion criteria

1. Reservation contracts have positive and negative exact-shape tests.
2. BFF tests prove the query allowlist, credential handling, identity rejection,
   upstream status handling, bounded errors, and `private, no-store` behavior.
3. Workspace tests prove provider selection, status filtering, pagination,
   accepted live fields, expansion, empty/restricted/unavailable states, and no
   patient identity claims.
4. Navigation mounts `/reservations`; no mutation control is enabled.
5. Repository formatting, lint, tests, build, and production dependency audit
   pass.
6. Exact-commit pull-request CI, review, and merge acceptance pass.

G3.5 completes only a read-only staff reservation visibility checkpoint. It
does not complete Gate 3 or authorize a reservation transition endpoint in the
browser.
