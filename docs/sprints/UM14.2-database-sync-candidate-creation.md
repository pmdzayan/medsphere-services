# UM14.2 — Database Synchronization & Candidate Creation

**Milestone:** 14 — Application Versioning & Update Management  
**Branch:** `cto/um14-2-database-sync-candidate-creation`  
**Stacked dependency:** PR #172 / UM14.1

## Objective

Build the repository-owned synchronization mechanism that refreshes the inactive BLUE/GREEN database from the current ACTIVE database, verifies the restored snapshot, emits synchronization evidence, and creates the proposed UM14.1 CANDIDATE state.

## Reuse

- Task 0022 PostgreSQL backup/restore core and integrity verifier.
- Task 0023 production runtime/deployment safety.
- Task 0050 release certification boundaries.
- Task 0058 measure-before-complexity governance.
- Task 0060 independent high-risk review.
- UM14.1 physical environment identities and transition validation.

No new datastore, replication service, queue, service mesh or deployment provider is introduced.

## Deliverables

- ADR-034 candidate snapshot rebuild decision.
- Executable UM14.2 safety policy.
- Guarded `blue-green-candidate-sync.mjs` CLI.
- Secret-free SHA-bound synchronization evidence.
- UM14.1-valid next-state generation.
- Unit tests for active-target protection, production-source binding, encrypted external snapshot storage, destructive confirmation and state transition.
- Operations runbook and project governance integration.

## Explicitly out of scope

- continuous logical/physical replication;
- dual writes;
- application traffic to the candidate;
- schema expand/contract migrations for the new release;
- shadow traffic;
- canary percentages;
- final cutover/catch-up;
- automatic rollback.

## Completion criteria

1. ACTIVE can never be the rebuild target.
2. Candidate must be the inactive ROLLBACK environment.
3. Source must exactly match the declared production database.
4. Source and candidate endpoints must differ.
5. Destructive rebuild requires an exact environment/database-identity confirmation.
6. Snapshot storage is external to the repository and acknowledged encrypted.
7. Candidate restore passes the existing Task 0022 integrity verifier.
8. Evidence contains no connection URLs, credentials or PHI.
9. Generated next state passes UM14.1 transition validation.
10. Focused tests and normal lint/test/build gates pass.
11. UM14.2 may not merge into the authoritative branch before UM14.1 is accepted and merged.
