## Objective

Implement ADR-012 as one assigned-provider command that moves an active,
unexpired batch into a terminal quarantine state, atomically cancels every
reservation holding that batch, preserves physical quantity, and records
immutable evidence without pretending release, recall, return, or disposal.

## HTTP and authorization contract

- Add only `POST /inventory/providers/:providerId/batches/:batchId/quarantine`
  in the accepted Inventory controller.
- Require authentication, trusted active membership/provider assignment, and
  migration-owned `inventory.batch.quarantine` permission granted only to
  active built-in `TENANT_ADMINISTRATOR` system roles.
- Use UUID-v4 path validation, global strict validation, private no-store
  responses, bounded safe errors, and Swagger documentation.
- Conceal missing, cross-tenant, deleted, inactive, and unassigned provider or
  batch resources as not found.
- Body fields are exactly:
  - `expectedVersion`: positive safe integer;
  - `idempotencyKey`: trimmed 8–120 character bounded string; and
  - `reasonCode`: `QUALITY_SUSPECT`, `TEMPERATURE_EXCURSION`,
    `PACKAGING_COMPROMISED`, or `STORAGE_DEVIATION`.
- Reject unknown fields and client-supplied tenant, actor, membership, product,
  inventory, quantity, status, timestamp, audit, permission, result, free-text,
  patient, or evidence fields.

## Transaction requirements

Run one serializable transaction with bounded retry:

1. Prove provider access from authenticated identity and load the exact scoped
   batch.
2. Authorize and compare replay only after provider access.
3. Require undeleted `ACTIVE`, unexpired state and exact expected version.
4. Probe affected active reservations in stable order with documented hard
   limits for reservations and total allocations.
5. Validate complete reservation item/allocation equality and require all
   allocations to remain `HELD`.
6. Reuse `releaseHeldAllocations` for every allocation of each affected
   reservation, including allocations on other batches.
7. Transition each affected reservation to `CANCELLED`, set one transaction
   timestamp, increment version, append one deterministic `CANCEL` command, and
   append one tenant-system `inventory.reservation.cancelled` audit with exact
   cause `BATCH_QUARANTINE`.
8. Prove candidate held quantity is zero and physical quantities are unchanged.
9. Conditionally set batch status to `QUARANTINED` and increment version once.
10. Insert one immutable `BatchQuarantineRecord` and one tenant-user
    `inventory.batch.quarantined` audit atomically.

Never clamp arithmetic, use application-only checks as the final authority,
start a nested transaction, or continue after a candidate invariant failure.

## Database and migration requirements

Add one forward migration that:

- adds `QUARANTINED` to `BatchStatus` without rewriting legacy meaning;
- creates immutable `BatchQuarantineRecord` with exact composite scope,
  allowlisted reason, actor membership, bounded counts, idempotency key,
  command hash, quantity snapshot, resulting version, and timestamps;
- enforces one quarantine record per batch and tenant-unique idempotency;
- adds query-driven indexes and an update/delete rejection trigger;
- adds migration-owned `inventory.batch.quarantine` permission only to active
  built-in `TENANT_ADMINISTRATOR` system roles without granting unrelated
  roles;
- extends audit event and metadata allowlists only for
  `inventory.batch.quarantined` and reservation cause `BATCH_QUARANTINE`;
- updates batch/status database checks without weakening quantity, tenant,
  movement, audit, or command invariants; and
- extends the populated-upgrade verifier through G3.11.

Update Prisma relations and enums. Prove clean deployment, no drift, populated
G3.10 upgrade preservation, invalid-row rejection, and permission convergence.

## Replay and response

- Canonical hash fields: tenant ID, provider ID, batch ID, expected version, and
  reason code.
- Same key and hash returns the immutable receipt only after current provider
  access; mismatched replay conflicts.
- Receipt fields are exactly batch ID, status `QUARANTINED`, reason code,
  unchanged on-hand quantity, affected reservation count, released unit count,
  resulting version, occurred-at timestamp, and `replayed`.
- Request metadata and actor do not alter the command hash. Audit still records
  the authenticated actor and bounded request metadata.

## Read and frontend compatibility

- Existing stock reads return `QUARANTINED` with available quantity zero.
- Update backend DTOs, frontend strict parser, parser tests, stock status label,
  and accessible visual treatment together.
- Do not add the quarantine mutation UI in this sprint. Existing accepted
  inventory screens remain read-only.

## Concurrency and integrity

Prove:

- exact replay changes nothing and returns the original receipt;
- mismatched replay conflicts without leaking prior data;
- two quarantine commands produce one transition, record, and audit;
- races with receipt, adjustment, transfer, damage, G3.10 expiry, reservation
  complete, cancel, and expiry have one valid winner;
- multi-reservation and multi-batch holds are fully released once;
- record, command, audit, permission, allocation, or conditional-write failure
  rolls back every effect; and
- no `StockMovement` exists for quarantine.

## Security and privacy

- Tenant, provider, product, inventory, batch, and actor scope derive only from
  authenticated context and database rows.
- Authorization occurs before replay disclosure.
- Audit actor is the trusted membership for the quarantine command; derived
  cancellation audits are tenant-system events with no user actor fields.
- DTOs, responses, logs, audits, and records contain no subject-user ID,
  patient identity, prescription data, notes, contact data, credentials,
  tokens, prices, request bodies, evidence URLs, or free text.
- Logs expose only allowlisted operation names, IDs where already permitted,
  reason code, bounded counts, result category, and request correlation.
