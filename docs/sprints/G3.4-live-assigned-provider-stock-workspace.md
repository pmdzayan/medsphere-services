# G3.4 Sprint Contract: Live Assigned-Provider Stock Workspace

**Status:** Accepted in PR #18 as `7b2eb78`; workflow `31278555022` passed

**Accepted base:** `9c387920cdea06798169175877b13a1394b183ec`

## Objective

Replace the inventory workspace's preview rows with the already accepted,
read-only provider stock contract without expanding mutation, business-policy,
or healthcare-data scope.

## Accepted dependencies

- authenticated session context from the sealed server-side profile;
- `GET /authorization/memberships/:membershipId/provider-access`;
- `GET /inventory/providers/:providerId/stock`;
- backend permission and live provider-assignment enforcement;
- G3.1 stock response fields and pagination semantics.

## Accepted scope

- list active providers assigned to the authenticated membership;
- allow the user to select among multiple assigned providers;
- load one assigned provider's paginated stock through a same-origin BFF;
- display product, brand, optional generic name/SKU, selling price, MRP,
  visibility, on-hand/held/available totals, and accepted batch fields;
- calculate only clearly labelled current-page counts or totals from returned
  data;
- provide loading, empty, restricted, malformed-upstream, unavailable, and
  retry states;
- keep successful and error responses non-cacheable;
- test exact request allowlists, exact upstream shapes, provider selection,
  pagination, filters supported by G3.1, and rendered states.

## Explicitly blocked

- receive, adjust, configure, transfer, return, damage, quarantine, recall,
  reservation, import, or barcode mutations;
- browser-supplied user, membership, tenant, role, permission, or access-token
  authority;
- rack location, category, reorder threshold, low-stock policy, expiry-risk
  window, analytics, or tenant-wide inventory value not present in the accepted
  response;
- patient, prescription, clinical, supplier, billing, delivery, or controlled-
  medicine data;
- changes to the database schema or accepted backend inventory semantics;
- routing through the health-only API-gateway scaffold before an application-
  composition contract is accepted.

## Same-origin BFF contracts

| Method | Browser route              | Accepted upstream route                                    |
| ------ | -------------------------- | ---------------------------------------------------------- |
| `GET`  | `/api/inventory/providers` | `/authorization/memberships/:membershipId/provider-access` |
| `GET`  | `/api/inventory/stock`     | `/inventory/providers/:providerId/stock`                   |

The provider-list BFF derives `membershipId` only from the integrity-protected
session profile. The stock BFF may accept a UUID `providerId` as a resource
selection, but never as proof of access; the backend's live assignment check
remains authoritative.

The stock BFF forwards only the G3.1 allowlist: `providerId`, `query`, `limit`,
and `offset`. Unknown query keys, duplicate scalar keys, invalid UUIDs, unsafe
integers, and overlong queries fail before the upstream call.

## Response validation

Both BFF routes reject successful upstream payloads unless they have exact
keys, accepted enums, canonical UUIDs, safe non-negative integer quantities,
bounded strings, valid ISO timestamps, decimal currency strings, and internally
consistent pagination. Each batch must satisfy the accepted availability
bound:

`0 <= availableQuantity <= onHandQuantity - heldQuantity`.

The upper bound permits the accepted backend to exclude expired, exhausted, or
otherwise ineligible units from availability. Item totals must equal the sums
of the returned batches and satisfy the same bound. The BFF does not silently
repair malformed upstream data.

## Security and privacy behavior

- Access and refresh credentials remain HTTP-only and are never returned to the
  browser.
- Browser-supplied tenant and membership identifiers are rejected or ignored;
  they are never forwarded.
- Upstream `401`, `403`, and `404` responses remain distinguishable only where
  the existing frontend security contract permits it. Response bodies stay
  bounded and do not leak upstream internals.
- Successful and error responses use `Cache-Control: private, no-store`.
- The UI does not render patient or reservation data.

## Completion criteria

1. Provider and stock contracts have positive and negative exact-shape tests.
2. BFF tests prove cookie handling, query allowlists, identity non-forwarding,
   upstream status handling, bounded errors, and `private, no-store` behavior.
3. Workspace tests prove provider selection, live rows, pagination/filtering,
   empty/restricted/unavailable states, and removal of preview claims.
4. No unsupported preview field or fabricated metric remains in the live stock
   workspace.
5. Repository formatting, lint, tests, build, and production dependency audit
   pass.
6. Exact-commit pull-request CI, review, and merge acceptance pass.

G3.4 completes only the read-only frontend integration checkpoint. It does not
complete Gate 3 or authorize any inventory mutation.
