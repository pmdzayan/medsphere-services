# G3.28 — Reservation Notification Operational Acceptance

## Objective

Complete the production-quality operational boundary for the accepted reservation notification workflow without activating external delivery or broadening scope.

## Required behavior

- metadata-only delivery status/evidence;
- no message-body, queued-variable, recipient-reference, contact-information, lock-token, or provider-reference leakage;
- active tenant-membership authorization for operational reads;
- tenant isolation across reads and metrics;
- bounded retry/dead-letter visibility;
- bounded status metrics;
- event IDs and correlation IDs;
- PostgreSQL readiness behavior that fails closed on dependency failure;
- structured privacy-safe operational logging;
- failure-mode and PostgreSQL-backed tenant-isolation tests;
- exact-head dependency audit, migration/drift, populated-upgrade, formatting, lint, test, and build gates.

## Explicit exclusions

No real notification provider, provider credentials, external delivery, Maps, FHIR, ABDM, billing, returns, recall, quarantine release, production deployment, or approval for real healthcare data.
