# G3.27 — End-to-End Queued Reservation Notification Workflow

**Status:** Implementation in progress

**Repository baseline:** `69d1400a461daf019dfd3be6da54d0a299cde835`

**Architecture authority:** ADR-015, ADR-016, ADR-017, ADR-018, and proposed ADR-019

## Objective

Connect the accepted reservation-ready event consumer, notification queue, recipient-resolution boundary, deterministic composition contract, and provider-neutral worker into the first bounded end-to-end notification workflow.

## In scope

- compose accepted queued reservation-ready variables before provider invocation;
- pass deterministic composed content through the provider-neutral adapter boundary;
- retain the notification delivery ID as the stable adapter idempotency key;
- preserve the unconfigured production provider registry as fail closed;
- prove duplicate event consumption creates one logical delivery;
- prove concurrent workers do not produce duplicate delivery attempts;
- prove bounded retry reuses the same logical idempotency key;
- preserve append-only attempt evidence and tenant-scoped recipient resolution;
- PostgreSQL integration coverage proportional to concurrency and retry risk.

## Out of scope

- real email, SMS, WhatsApp, push, or other external provider activation;
- provider credentials or destination persistence;
- arbitrary message bodies or general-purpose templating;
- Maps, FHIR, ABDM, Blood Bank, billing, returns, recall, quarantine release;
- production deployment or real healthcare data approval.

## Acceptance criteria

1. `inventory.reservation.ready` v1 reaches the accepted queue only through the G3.24 durable inbox consumer.
2. The worker resolves the recipient and runs G3.26 deterministic composition before any provider invocation.
3. Unsupported template data fails closed before provider invocation.
4. Duplicate consumption creates one notification delivery.
5. Concurrent workers create one logical successful delivery.
6. Retry attempts reuse the same notification delivery ID as the provider idempotency key.
7. Attempt evidence remains append-only and no recipient contact information is persisted into event or queue payloads.
8. Production remains fail closed because no real provider registry is approved.
9. Formatting, lint, architecture checks, unit tests, PostgreSQL integration tests, build, and exact-head GitHub CI pass before acceptance.

## Completion meaning

Passing G3.27 proves the bounded queued reservation notification workflow and its retry/concurrency behavior against a safe test adapter. It does not prove real external delivery or operational production acceptance; G3.28 remains required.
