# G3.12 Sprint Contract: Live Batch Quarantine Workspace

**Status:** Accepted and squash-merged in PR #41 as `85fdf53` after exact-head
CI run `31762213509` passed all required gates.

**Accepted implementation base:** `0bfe951fb2994beb8acf3bfb3721d8b2c5b36b21`

## Objective

Connect the accepted G3.11 one-way batch quarantine command to the existing
assigned-provider inventory workspace without weakening provider assignment,
permission, optimistic-concurrency, idempotency, or audit authority.

## In scope

- expose the positive batch version in the accepted stock read as a command
  concurrency token;
- add exact frontend request and receipt contracts for the four accepted reason
  codes;
- add one same-origin, authenticated, private no-store BFF mutation route;
- forward only provider ID, batch ID, expected version, idempotency key, and
  allowlisted reason code;
- show the action only for currently `ACTIVE` batches;
- require explicit confirmation that reservations can be cancelled, holds are
  released, physical stock is preserved, and V1 has no reversal;
- reuse one idempotency key while the confirmation remains open;
- refresh authoritative stock after success and show the bounded immutable
  receipt summary; and
- cover stock-version propagation, strict parsing, BFF rejection, version
  conflict, success, refresh, and error behavior with tests.

## Authority and safety rules

- The browser never supplies tenant, actor, membership, quantity, free text, or
  audit fields.
- The backend remains authoritative for trusted identity, provider assignment,
  command permission, state, expiry, expected version, transaction, reservation
  cancellation, physical quantity, idempotency, and audit evidence.
- A visible button does not claim permission. A backend denial remains a denial
  and is surfaced as a bounded error.
- A conflict is not retried with a fabricated version. Staff must reload live
  stock before issuing a new command.
- Quarantined stock remains visible as physical stock with zero availability.

## Explicit exclusions

- quarantine release, recall, disposal, supplier return, refund, or approval;
- custom/free-text reasons, attachments, notes, or evidence upload;
- patient, public, marketplace, notification, analytics, or gateway behavior;
- new permissions, database migrations, background workers, or services; and
- production or compliance approval.

## Acceptance gate

The sprint may be accepted only when formatting, lint, unit tests, frontend
route/component tests, full monorepo tests, build, dependency audit, database
migration/drift checks, populated-upgrade verification, exact-head CI, and CTO
review all pass.
