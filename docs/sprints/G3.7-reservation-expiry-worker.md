# G3.7 Sprint Contract: Reservation Expiry Worker

**Status:** Proposed; CTO contract acceptance required before implementation

**Accepted base:** `3327d01c69d208333a141e39fc3f95f822d408f1`

## Objective

Implement the automatic expiry boundary already required by ADR-005. A bounded,
non-HTTP worker must find due active medicine reservations, atomically release
their exact held batch allocations, transition them to `EXPIRED`, and append
tenant-scoped system audit evidence.

This sprint closes leaked-hold risk. It does not expose reservation creation or
add another reservation owner.

## Accepted dependencies

- ADR-001, ADR-002, ADR-003, ADR-004, ADR-005, ADR-006, ADR-007, and ADR-008;
- the accepted modular-monolith inventory composition in `auth-service`;
- `MedicineReservation`, item, allocation, command, batch, and audit schema;
- the existing `EXPIRE` command type and `inventory.reservation.expired` audit
  event;
- PostgreSQL serializable retry, batch quantity checks, reservation state
  checks, allocation state checks, and tenant-system audit support; and
- the accepted G3.3 staff transition behavior.

## Ownership and execution boundary

- Expiry belongs to the Inventory bounded context mounted in `auth-service`.
- Do not add behavior to the prototype `reservation-service` or duplicate the
  unmounted `inventory-service` implementation.
- Implement one standalone, one-shot application-context worker. It must not
  open an HTTP listener.
- An external scheduler may invoke the process later. This sprint does not
  claim a production schedule or deployment that does not exist.
- The process exits successfully only when the bounded run completes without
  unexpected reservation failures. It exits non-zero after reporting bounded,
  non-sensitive failure counts when any selected reservation fails.

## Selection contract

- Capture one authoritative `asOf` timestamp for each run.
- Select only `PENDING`, `CONFIRMED`, or `READY` reservations whose
  `expiresAt <= asOf`.
- Selection is cross-tenant but processing is tenant-scoped from the selected
  database row. No caller supplies tenant identity.
- Use the existing due-reservation index and stable order:
  `expiresAt`, `tenantId`, `id`.
- A run has explicit positive safe-integer batch and maximum-record limits.
  Defaults and hard maximums must be documented and tested.
- Never load an unbounded result set or loop indefinitely.

## Atomic expiry contract

Process each selected reservation in its own serializable transaction with
bounded retry:

1. Re-read the exact tenant, provider, reservation, active status, version, and
   due timestamp inside the transaction.
2. Treat a reservation that is no longer due or active as a safe concurrent
   skip. Do not overwrite a completed or cancelled transition.
3. Load every allocation in stable `id` order and require all expected
   allocations to remain `HELD`.
4. Require held allocation totals to equal requested item totals.
5. Decrement each exact batch's `heldQuantity` without changing
   `onHandQuantity`; increment the batch version; never clamp arithmetic.
6. Mark each allocation `RELEASED` with the same `asOf` timestamp.
7. Conditionally transition the reservation to `EXPIRED`, set `expiredAt` to
   `asOf`, and increment its version.
8. Insert one `MedicineReservationCommand` with type `EXPIRE`, a deterministic
   tenant-scoped idempotency key and command hash, and the resulting version.
9. Append one `inventory.reservation.expired` tenant-system audit event in the
   same transaction.

Any missing allocation, quantity mismatch, batch underflow, stale batch
version, invalid state, command conflict, or audit failure rolls back the whole
reservation expiry.

## Concurrency and idempotency

- Multiple worker processes may overlap safely.
- A worker may race with confirm, ready, complete, or cancel. Exactly one valid
  state change wins; a terminal staff transition must never be overwritten.
- Re-running after success must not release stock twice, create duplicate
  commands, or append duplicate audit events.
- Batch updates use exact tenant/provider/inventory/product scope plus expected
  quantities and version.
- Serialization conflicts use the accepted bounded retry helper. Other errors
  are not swallowed or relabelled as success.

## Security, privacy, and audit

- No browser or HTTP route is added.
- No tenant, membership, role, permission, user, or access-token identity is
  accepted from a caller.
- Audit uses `TENANT` scope and `SYSTEM` actor with no user actor fields.
- Audit metadata is allowlisted and may contain only previous status,
  resulting version, total released units, and expiry timestamp.
- Logs and run summaries contain bounded counts and error categories only. They
  must not contain patient/user identity, prescription or clinical data,
  reservation notes, request bodies, credentials, or access tokens.

## Explicitly blocked

- public or staff reservation creation;
- patient self-service, Marketplace authorization, or subject-user policy;
- new HTTP, browser, BFF, API-gateway, or mutation UI behavior;
- reservation confirmation, ready, completion, or cancellation redesign;
- transfers, returns, damage, quarantine, recall, physical stock expiry, or
  analytics;
- notification delivery or event-outbox claims;
- a new queue, scheduler dependency, database schema, permission, or audit
  event unless repository inspection proves the accepted support is unusable.

## Testing requirements

Add unit and real-PostgreSQL tests proving:

1. bounded stable due selection and hard configuration limits;
2. expiry from each active state and exclusion of future or terminal records;
3. exact release of multi-item, multi-batch holds with unchanged on-hand stock;
4. reservation, allocation, command, batch-version, and audit writes share one
   transaction and timestamp;
5. tenant-system audit shape contains no user actor or sensitive metadata;
6. repeat execution is idempotent;
7. two workers racing produce one expiry and one release;
8. expiry racing with staff cancellation or completion has one valid winner;
9. malformed allocation totals, insufficient held stock, audit failure, and
   command conflict roll back completely;
10. one failed reservation is counted, does not fabricate success, and does
    not prevent other selected reservations from being attempted;
11. unexpected failures cause a non-zero process exit;
12. no HTTP route, permission, browser identity, or second domain owner is
    introduced.

Do not weaken, delete, skip, or replace existing tests.

## Validation

Run and report:

- `pnpm install --frozen-lockfile`;
- focused worker unit tests;
- real PostgreSQL expiry integration and concurrency tests;
- `pnpm audit:prod`;
- `pnpm format:check`;
- `pnpm lint`;
- `pnpm test`;
- `pnpm build`;
- `git diff --check`; and
- the established clean migration, populated-upgrade, and drift gates.

Skipped or infrastructure-blocked commands must be reported exactly.

## Completion criteria

1. The bounded one-shot worker expires due active reservations without an HTTP
   boundary.
2. Exact held allocations are released atomically and on-hand stock is
   unchanged.
3. Concurrency, idempotency, tenant scope, rollback, audit, and process failure
   behavior pass real PostgreSQL tests.
4. No creation, patient, frontend, gateway, permission, schema, notification,
   or unrelated inventory behavior changes.
5. Exact-commit pull-request CI, CTO review, and merge acceptance pass.

After implementation acceptance, the evidence-weighted V1 estimate may move
from 31% to approximately 32%. Contract definition alone does not change the
percentage.
