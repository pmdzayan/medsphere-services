## Objective

Implement ADR-009 as one authenticated command that truthfully records an
already completed physical transfer of one batch quantity between two assigned
provider locations in the same tenant. Both stock sides, ledger movements,
idempotency receipt, immutable transfer record, and tenant audit evidence must
commit atomically.

This sprint closes only completed-transfer recording. It does not claim a
shipment or in-transit workflow.

## Database contract

Add one forward migration and Prisma representation for the immutable
`InventoryTransfer` receipt. The final design must include:

- UUID primary key and explicit tenant ID;
- source/destination provider IDs, which must differ;
- product, source/destination inventory, source/destination batch IDs;
- positive quantity;
- external idempotency key, 64-character lowercase SHA-256 command hash;
- source/destination stock movement IDs;
- database-generated completion timestamp;
- composite foreign keys proving same-tenant and provider/product scope;
- tenant-unique idempotency key;
- query-driven indexes for tenant/provider/time and transfer lookup;
- check constraints for different providers, positive quantity, and hash shape;
  and
- PostgreSQL trigger rejecting update and delete.

Extend migration-owned policy with exactly:

- permission `inventory.stock.transfer`, assigned to the built-in tenant
  administrator role; and
- audit event `inventory.stock.transferred` with metadata keys
  `sourceProviderId`, `destinationProviderId`, `productId`, and `quantity`.

Migration preflight and upgrade logic must fail closed on incompatible existing
data. Do not edit accepted migrations.

## API contract

Add one command under the accepted Inventory controller, equivalent to:

`POST /inventory/providers/{sourceProviderId}/transfers`

The body accepts only:

- `destinationProviderId` — UUID v4;
- `sourceBatchId` — UUID v4;
- `expectedSourceVersion` — positive safe integer;
- `quantity` — positive safe integer;
- `idempotencyKey` — trimmed, bounded, non-empty command key; and
- optional normalized bounded non-sensitive reason.

The response contains only the completed transfer receipt:

- transfer ID;
- source and destination provider, inventory, and batch IDs;
- product ID and quantity;
- source and destination movement IDs;
- source and destination on-hand results and batch versions;
- completion timestamp; and
- `replayed` boolean.

Return the shared safe error envelope. Document authentication, permission,
not-found, validation, conflict, and success responses in Swagger. Preserve
private/no-store behavior.

Do not accept tenant, membership, user, role, permission, actor, inventory,
destination batch, movement, price, or status authority from the request.

## Authorization contract

- Require `inventory.stock.transfer`.
- Resolve tenant and actor only from `AuthenticatedIdentity`.
- Require live provider assignment to both source and destination.
- Verify both assignments before reading an idempotency receipt.
- Missing, inactive, deleted, cross-tenant, or unassigned source/destination
  providers return the same not-found boundary.
- Revoked provider access must conceal prior receipts.
- Same-provider transfer is validation failure and performs no database writes.

## Atomic command contract

Execute one serializable transaction with bounded retry:

1. Authorize both providers and check an exact replay.
2. Capture one database timestamp.
3. Re-read the exact source batch/listing and expected version.
4. Reject deleted, non-active, expired, malformed, or insufficiently available
   source stock. Quantity cannot consume held units.
5. Require an undeleted destination listing for the same product.
6. Conditionally decrement only source on-hand quantity and increment version;
   preserve held and received quantities.
7. Match destination batch by batch number and exact provenance. On a match,
   increment destination received and on-hand quantities and version. On no
   match, create one destination batch from exact source provenance.
8. Write reconciled `TRANSFER_OUT` and `TRANSFER_IN` movements with distinct
   derived idempotency keys, the same transfer reference and command hash, and
   the authenticated tenant-user actor.
9. Write the immutable transfer receipt and typed tenant-user audit event.
10. Return the stored receipt.

All quantity, version, provenance, unique, command, movement, and audit failures
roll back the complete transfer. Never clamp, partially commit, silently retry
non-serialization errors, or relabel failure as success.

## Destination batch rules

- Destination inventory configuration must already exist; never copy or invent
  SKU, MRP, discount, tax, visibility, or minimum-stock policy.
- Batch number, manufacturing date, expiry date, purchase price, and batch
  selling price are transfer provenance.
- A matching destination batch with different provenance is a conflict.
- An expired source batch cannot transfer.
- An exhausted destination batch may become active only when its provenance is
  exact and new positive stock is added.
- A destination batch marked expired fails closed even if its stored date is
  inconsistent with that status.
- Deleted batches are never resurrected or silently replaced.

## Idempotency and concurrency

- Canonicalize and hash every accepted command field plus trusted tenant scope.
- Exact replay returns the original receipt after current dual-provider access
  checks.
- Same key with a different hash conflicts.
- Concurrent use of one source version has one winner.
- Concurrent creation or increment of the same destination batch cannot lose
  stock, duplicate the batch, or duplicate ledger/audit evidence.
- A serialization failure uses the existing bounded retry helper.

## Security and privacy

- No client-supplied trusted identity or tenant context.
- No patient, prescription, clinical, delivery, payment, supplier, credential,
  token, or controlled-medicine data.
- Free-text reason is bounded, non-clinical, never logged, and not copied into
  audit metadata.
- Audit is tenant-user scoped and atomic with the mutation.
- Operational logs contain bounded categories/counts only.
- Do not weaken global authentication, provider concealment, permission denial,
  validation, Helmet, throttling, request-ID, no-store, or error behavior.

## Explicitly out of scope

- dispatch, shipment, in-transit, receipt, rejection, cancellation, reversal,
  discrepancy, loss, or approval states;
- partial, multi-line, multi-batch, cross-tenant, supplier, patient, delivery,
  or controlled-medicine transfers;
- warehouses or sublocations within one provider;
- automatic destination listing creation;
- reservation allocation movement;
- notifications, outbox/events, analytics, transfer history UI, or mutation UI;
- API-gateway routing changes, another service, scheduler, or deployment; and
- returns, damage, quarantine, recall, expiry disposal, or generic adjustment
  redesign.

## Testing requirements

Add unit, HTTP, migration, and real PostgreSQL tests proving:

1. strict DTO validation and rejection of unexpected/client-authority fields;
2. permission and live assignment to both providers;
3. identical concealment for missing, cross-tenant, inactive, or unassigned
   providers;
4. authorization occurs before replay lookup;
5. same-provider, future/deleted/expired source, stale version, non-positive,
   unsafe, and held-stock quantities fail closed;
6. exact source decrement and destination create path conserve total on-hand;
7. exact destination merge path increments received/on-hand and preserves held;
8. provenance mismatch rolls back;
9. two reconciled immutable movements and one immutable transfer record;
10. audit allowlist, tenant-user actor, resource, and no sensitive metadata;
11. exact idempotent replay and same-key/different-hash conflict;
12. concurrent source transfers have one winner;
13. concurrent destination merge/create cannot lose or duplicate stock;
14. movement, receipt, or audit failure rolls back both batch changes;
15. direct transfer-record update/delete is rejected by PostgreSQL;
16. existing listing, receipt, adjustment, reservation, and expiry behavior does
    not regress; and
17. no new HTTP route exists outside the accepted Inventory controller.

Do not weaken, delete, skip, or replace existing tests.

## Completion criteria

1. One completed transfer conserves stock atomically across two assigned
   same-tenant provider locations.
2. Held stock, batch provenance, versions, ledger equations, idempotency, and
   audit evidence remain correct under concurrency and failure.
3. No shipment, transit, patient, supplier, delivery, payment, frontend,
   gateway, notification, or unrelated inventory behavior is claimed.
4. Clean and populated migration evidence and all exact-commit gates pass.
5. CTO review and merge acceptance pass.

Verified implementation acceptance moves the V1 estimate to 33%. This is an
engineering progress estimate, not a production-readiness claim.
