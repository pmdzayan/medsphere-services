# G3.24 — Reservation-Ready Notification Consumer

**Status:** Implementation in review

**Repository baseline:** `2fbe336cc0fc15f5ddfc05e74d719be1fd2c4182`

**Architecture authority:** ADR-003, ADR-004, ADR-005, ADR-008, ADR-013,
ADR-014, ADR-015, and proposed ADR-016

## Objective

Create the bounded, tenant-safe, idempotent bridge from the accepted
`inventory.reservation.ready` version-1 event to one provider-neutral G3.23
notification intent.

## In scope

- authoritative event reload inside the G3.21 inbox transaction;
- exact event name, version, aggregate, and payload validation;
- authoritative tenant/reservation/provider verification;
- opaque same-tenant membership recipient reference;
- one fixed reservation-ready workflow, channel, template reference, and
  structured status variable;
- duplicate/replay suppression and rollback-safe processing evidence; and
- unit plus PostgreSQL replay, rollback, isolation, and immutability tests.

## Out of scope

- recipient destination/contact resolution or authorization policy;
- generalized composition, rendering, localization, or arbitrary text;
- event relay scheduling or an operational endpoint;
- real provider adapters, credentials, or external calls;
- other reservation transitions or inventory events;
- Maps, FHIR, ABDM, billing, returns, recall, quarantine release, frontend,
  production deployment, or real healthcare data.

## Acceptance criteria

1. Only `inventory.reservation.ready` version 1 with the exact accepted schema
   creates an intent.
2. The event and reservation are reloaded and tenant-matched inside the inbox
   transaction.
3. Duplicate or concurrent replay produces one inbox receipt and one delivery.
4. Any downstream failure rolls back the receipt and queue effect.
5. Cross-tenant processing fails without evidence or delivery leakage.
6. The queue and receipt contain no contact, patient identity, clinical data,
   message body, or free text.
7. Formatting, lint, tests, build, PostgreSQL integration, architecture checks,
   and exact-head GitHub CI pass before acceptance.

## Completion meaning

Passing G3.24 proves only the event-to-intent consumer contract. It does not
prove recipient resolution, composed content, provider delivery, an active
worker schedule, or production readiness.
