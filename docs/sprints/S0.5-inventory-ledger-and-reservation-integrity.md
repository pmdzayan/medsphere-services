# Sprint S0.5 — Inventory Ledger and Medicine Reservation Integrity

**Owner:** ChatGPT / Codex (CTO and large-task implementer)

**Status:** Architecture accepted; checkpoint publication and CI pending

**Branch:** `cto/s0.5-inventory-reservation-integrity`

**Accepted base:** `4ea55a17e188410ddee45fa3ea6c016e22d6617a`

**Dependency:** S0.4 accepted and squash-merged in PR #7

**Decision:** ADR-005

## Objective

Replace the prototype stock and reservation persistence boundaries with one
tenant-safe batch stock model, one append-only movement ledger, and one atomic
medicine-reservation hold lifecycle. Prove clean and populated migration safety,
rollback, idempotency, deterministic FEFO, concurrency, authorization, audit,
and route isolation before accepting any inventory or reservation behavior.

## Repository findings that define the work

1. `Inventory.quantity` and `Batch.currentQuantity` are competing stock sources.
2. `Inventory` has batch fields but no relationship to `Batch`.
3. `StockMovement` and `InventoryHistory` duplicate mutable history.
4. repository calls inside transaction callbacks use the root Prisma client.
5. stock arithmetic is read-then-write and loses updates under concurrency.
6. `Math.max(0, ...)` hides batch underflow.
7. FEFO reads are not protected by the writes they drive.
8. reservation structure is stored in JSON `notes`.
9. medicine reservation behavior is duplicated across two applications.
10. reservation-service uses a hard-coded all-zero user identifier.
11. stock and reservation records lack explicit tenant scope and same-tenant
    composite foreign keys.
12. current tests mock the transaction client and cannot prove atomicity.

These are acceptance blockers, not optional cleanup.

## Target persistence contract

### Inventory

- exactly one active row per `(tenantId, providerId, productId)`;
- contains listing and commercial configuration only;
- contains no on-hand, held, batch, expiry, or derived availability state;
- composite tenant/provider relationships prevent cross-tenant relabeling;
- optimistic version supports administrative configuration updates.

### Batch

- belongs to one inventory listing;
- same tenant/provider/product scope enforced in PostgreSQL;
- unique batch number within tenant/provider/product;
- positive received quantity;
- `onHandQuantity >= 0`;
- `heldQuantity >= 0`;
- `heldQuantity <= onHandQuantity`;
- valid manufacturing/expiry ordering;
- query index for tenant/provider/product/status/expiry FEFO access;
- status and deletion cannot make expired stock sellable.

### StockMovement

- one batch and inventory per entry;
- non-zero signed delta;
- `onHandAfter = onHandBefore + delta`;
- tenant, provider, product, actor, reference, idempotency, and occurrence data;
- append-only trigger rejects update and delete;
- stable query indexes and tenant-scoped idempotency uniqueness;
- no `version`, `updatedAt`, `deletedAt`, or duplicate snapshot table.

### MedicineReservation

- tenant/provider header with authenticated subject user;
- explicit status, expiry, timestamps, version, idempotency key, and bounded notes;
- one or more typed items;
- one or more exact batch allocations per item;
- held, consumed, and released allocation outcomes are mutually consistent;
- stable indexes for tenant/provider/status/expiry, subject history, and workers.

## Required invariants

1. Available stock is the sum of eligible batch
   `onHandQuantity - heldQuantity`.
2. Expired, exhausted, deleted, or invisible stock is not sellable.
3. A reservation never holds more units than are available.
4. One batch unit cannot be held by two reservations.
5. Complete consumes exactly the reservation's held allocations.
6. Cancel or expire releases every held allocation exactly once.
7. A terminal reservation never transitions again.
8. Every on-hand mutation has one immutable stock movement.
9. Every sensitive mutation has one atomic durable audit event.
10. Retry of an idempotent command does not duplicate stock, reservation,
    movement, allocation, or audit rows.
11. Tenant/provider/inventory/batch/reservation/actor relationships cannot cross
    tenants.
12. A failed write, audit insert, movement insert, or status transition leaves
    no partial state.

## Transaction and concurrency requirements

- Use the same `Prisma.TransactionClient` for all reads and writes in a command.
- Use PostgreSQL serializable isolation with bounded retry for serialization
  conflicts.
- Lock or conditionally update affected batches in deterministic FEFO order.
- Reject, never clamp, negative or over-held quantities.
- Use expected versions for reservation and mutable configuration transitions.
- Use tenant-scoped idempotency keys for retriable commands.
- Prove competing reserve, complete, cancel, expire, receive, and adjustment
  scenarios with real PostgreSQL concurrency tests.

## Authorization and audit requirements

- Trusted identity supplies tenant and actor membership.
- Provider and resource identifiers are verified inside that tenant.
- No request may select its authoritative tenant or actor.
- Permission keys are migration-owned and added only for mounted S0.5 routes.
- Tenant administrators receive new accepted capabilities only through the
  reviewed migration.
- Staff mutations use tenant-user audit attribution.
- expiry workers use tenant-scoped system attribution accepted by ADR-005.
- Event metadata is allowlisted, bounded, and non-clinical.
- Audit failure rolls back the protected mutation.

## Migration requirements

- Start from the accepted S0.4 migration chain without editing it.
- Add forward-only S0.5 migration(s).
- Backfill tenant scope from provider relationships.
- Reconcile legacy inventory quantities to batch totals.
- Consolidate only compatible provider-product inventory configuration.
- Prove legacy history is represented before retiring `InventoryHistory`.
- Reject ambiguous held quantity and reservation JSON rather than guessing.
- Reject non-medicine reservation rows rather than converting them.
- Never print patient or clinical data in migration diagnostics.
- Extend `db:verify-upgrade` or add an equally explicit S0.5 verifier with:
  - valid populated conversion;
  - inventory/batch mismatch rejection;
  - incompatible duplicate inventory rejection;
  - cross-tenant relationship rejection;
  - unmatched history rejection;
  - ambiguous held stock/reservation rejection; and
  - invalid quantity/state rejection.

## Application requirements

- Repositories accept an explicit database/transaction client.
- Domain commands do not call controllers or repositories in another app.
- FEFO planning and mutation occur inside the protected transaction.
- Reservation structure uses typed columns and relations, never JSON notes.
- Automatic expiry is observable, retry-safe, bounded, and does not swallow
  failures.
- Read models aggregate batches with bounded, indexed queries.
- Existing error, validation, logging, identity, authorization, and audit
  patterns are reused.
- Duplicate reservation logic is removed only after replacement behavior and
  migration are proven.

## API boundary

S0.5 may mount only routes explicitly listed in the implementation checkpoint.
Every mounted route must have:

- authentication and tenant context;
- permission requirements;
- UUID and DTO validation;
- version or idempotency preconditions where required;
- bounded pagination and allowlisted filters;
- Swagger request, response, and error contracts;
- tenant-isolation and negative-authorization tests; and
- atomic audit behavior.

Public patient reservation creation, delivery, payment, and controlled-medicine
routes remain unmounted.

## Testing requirements

### Unit

- quantity and state invariants;
- signed movement semantics;
- FEFO ordering including equal-expiry tie breakers;
- reservation transition matrix;
- idempotency behavior;
- DTO and metadata validation.

### PostgreSQL integration

- every check, unique key, and composite foreign key;
- append-only movement trigger;
- valid populated S0.4 conversion;
- migration failure scenarios;
- atomic mutation/audit rollback;
- concurrent reserve without oversell;
- concurrent complete/cancel/expire with one winner;
- concurrent stock adjustments without lost updates;
- exact allocation release and consumption;
- deterministic FEFO under contention.

### HTTP and security

- no hard-coded or client-controlled identity;
- cross-tenant reads and writes return no foreign data;
- missing/unknown permissions deny;
- malformed/stale versions and idempotency keys fail;
- unaccepted routes remain unreachable;
- supported languages remain `en`, `hi`, `ta`, `te`, and `kn`.

Mocks must accept and assert the transaction client. A mock that executes a
callback while repositories use unrelated clients is rejected.
