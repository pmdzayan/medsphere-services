# S0.4 Sprint Specification: Tenant-Safe RBAC and Durable Audit

**Owner:** ChatGPT / Codex (CTO and large-task implementer)

**Status:** Implementation and local review complete; PostgreSQL/Redis CI
acceptance pending

**Dependency:** S0.3 accepted and merged; S0.3 documentation handoff verified

**Decision:** ADR-004

## Objective

Replace the tenant-unsafe RBAC and mutable audit prototypes with a
membership-scoped authorization boundary and append-only durable audit trail.
Mount only the accepted S0.4 administration and tenant-audit APIs. Prove tenant
isolation, fail-closed authorization, audit atomicity, immutability, migration
safety, and concurrent last-administrator protection.

## Repository analysis

The sprint contract follows direct repository review:

- `UserRole` assigns `Role` to global `User`, not `TenantMembership`.
- role, permission, and assignment repository methods permit missing tenant
  filters.
- `PermissionsGuard` looks up a global user's permissions and accepts arbitrary
  metadata strings.
- role DTOs accept client-provided `tenantId`, `type`, and permission IDs.
- `RbacSeedService` creates dozens of premature permissions at runtime, catches
  errors, and continues startup.
- built-in roles use a nonexistent zero-UUID tenant.
- role mutation is not atomic and has no concurrency precondition.
- the last tenant administrator can be removed.
- `AuditLog` has no actor/tenant foreign keys, accepts arbitrary snapshots, and
  can be updated or deleted.
- audit reads accept client-selected organization scope and unbounded dynamic
  sort fields.
- S0.3 already provides trusted `userId`, `membershipId`, `tenantId`,
  `sessionId`, typed validation, shared error handling, OpenAPI setup, and an
  allowlisted authentication security-event seam.
- RBAC and audit prototype modules are deliberately unmounted in `AppModule`.

## In scope

### Database

- Replace global-user role assignments with membership role assignments.
- Add composite tenant keys and foreign keys for memberships, roles,
  assignments, and role-permission relationships.
- Make the permission catalogue global and migration-owned.
- Insert the exact eight S0.4 permissions with stable identifiers.
- Create one built-in `TENANT_ADMINISTRATOR` role per tenant without assigning
  it automatically.
- Migrate only unambiguous, valid legacy assignments; stop on unsafe legacy
  roles, permission mappings, assignments, or mutable audit rows.
- Replace `AuditLog` with typed `AuditEvent`.
- Add actor/scope/outcome checks, JSON object/size checks, query-driven indexes,
  and an update/delete rejection trigger.
- Add clean-install and S0.3-upgrade migration verification.

### Authorization

- Add typed permission constants and reject unknown keys at metadata creation.
- Resolve permissions from the verified membership and tenant on every request.
- Mount tenant-scoped role, permission, and assignment APIs.
- Derive tenant from `AuthenticatedIdentity`; do not accept it from the client.
- Use strong `If-Match` role versions for update and delete.
- Keep built-in role names and permissions immutable.
- Protect last-administrator removal with serializable transactions and bounded
  retry.
- Return generic tenant-safe not-found/forbidden errors without confirming
  cross-tenant identifiers.

### Durable audit

- Add an internal append-only audit writer with typed event definitions and
  allowlisted metadata builders.
- Write role and assignment events atomically with their mutations.
- Integrate attributable authentication session events.
- Record global logout-all as a platform-user event, not as a misleading
  tenant-scoped aggregate.
- Expose bounded, cursor-based tenant audit reads guarded by
  `audit.events.read`.
- Never expose platform events through the tenant API.

### API contract

| Method   | Route                                                    | Permission                         | Concurrency |
| -------- | -------------------------------------------------------- | ---------------------------------- | ----------- |
| `GET`    | `/authorization/permissions`                             | `authorization.permissions.read`   | —           |
| `GET`    | `/authorization/roles`                                   | `authorization.roles.read`         | —           |
| `POST`   | `/authorization/roles`                                   | `authorization.roles.create`       | —           |
| `GET`    | `/authorization/roles/:roleId`                           | `authorization.roles.read`         | —           |
| `PATCH`  | `/authorization/roles/:roleId`                           | `authorization.roles.update`       | `If-Match`  |
| `DELETE` | `/authorization/roles/:roleId`                           | `authorization.roles.delete`       | `If-Match`  |
| `GET`    | `/authorization/memberships/:membershipId/roles`         | `authorization.assignments.read`   | —           |
| `PUT`    | `/authorization/memberships/:membershipId/roles/:roleId` | `authorization.assignments.manage` | —           |
| `DELETE` | `/authorization/memberships/:membershipId/roles/:roleId` | `authorization.assignments.manage` | —           |
| `GET`    | `/audit/events`                                          | `audit.events.read`                | cursor      |
| `GET`    | `/audit/events/:eventId`                                 | `audit.events.read`                | —           |

All identifier parameters use UUID validation. Role names, descriptions,
permission keys, audit filters, cursors, and page sizes are bounded and
allowlisted. Unexpected body fields are rejected by the existing global
validation pipe.

## Out of scope

- Platform administrator, support impersonation, delegated access, and
  break-glass policy
- Arbitrary tenant-defined permission capabilities
- ABAC/policy engine, consent, privacy center, retention, archival, legal hold,
  or audit export
- Inventory, reservation, supplier, pharmacy, hospital, doctor, laboratory,
  patient, marketplace, delivery, payment, analytics, reporting, or frontend
  work
- Controlled-medicine workflows
- Authorization caching, permission JWT claims, audit outbox delivery, audit
  cryptographic signing, or a new service
- Production-readiness or legal-compliance certification

## Required security and integrity tests

- Same global user with memberships in two tenants receives only the active
  membership's permissions.
- Forged tenant/user headers never affect authorization.
- Missing or unknown permission metadata denies activation/startup.
- Cross-tenant membership-role inserts fail at the database.
- Cross-tenant role-permission inserts fail at the database.
- Soft-deleted roles and inactive memberships never authorize.
- Tenant APIs cannot read or mutate another tenant's role, assignment, or audit
  event by identifier.
- Missing, weak, malformed, and stale `If-Match` values fail correctly.
- Concurrent role version updates allow one winner.
- Concurrent last-administrator removals preserve at least one assignment.
- Built-in role rename, deletion, and permission replacement are rejected.
- Audit event update and delete fail in PostgreSQL.
- Invalid actor/scope combinations and oversized/non-object metadata fail.
- Audit failure rolls back the protected role or assignment mutation.
- Session mutation failure rolls back its required audit event and vice versa.
- Global logout-all evidence is platform-scoped and not leaked by tenant reads.
- Query pagination is bounded and stable for equal timestamps.
- Supported languages remain `en`, `hi`, `ta`, `te`, and `kn`.
- Every still-unaccepted prototype route remains unmounted.

## Implementation sequence and checkpoints

1. **Architecture checkpoint:** ADR-004, this sprint contract, indexes, status,
   roadmap, handoff.
2. **Database checkpoint:** Prisma schema, forward migration, clean/upgrade SQL
   verification, generated client.
3. **Authorization checkpoint:** permission catalogue, repository, service,
   guards, DTOs, controllers, unit and HTTP tests.
4. **Audit checkpoint:** append-only writer, authentication integration,
   atomicity, tenant read APIs, unit and HTTP tests.
5. **Infrastructure checkpoint:** PostgreSQL/Redis suites, concurrency,
   migration/drift, CI wiring.
6. **Acceptance checkpoint:** full review, Development Bible, status, roadmap,
   handoff, draft PR.

Every checkpoint is committed and pushed before the next begins.

## Completion criteria

- ADR-004 and all affected Development Bible volumes match the implementation.
- The migration deploys cleanly and from the accepted S0.3 schema with no
  drift.
- PostgreSQL proves same-tenant assignment integrity and audit immutability.
- Every accepted endpoint is typed, documented, bounded, tenant-scoped,
  authenticated, and permission-guarded.
- Authorization is fail-closed and derived only from the trusted S0.3 identity.
- Role and assignment mutations are atomic with required audit events.
- Authentication session evidence is durable and correctly scoped.
- Concurrency tests protect role versions and the last administrator.
- All unaccepted modules remain unreachable.
- Format, database, lint, test, build, CI, security, performance, duplicate-code,
  and architecture reviews pass.
- The CTO performs final acceptance before S0.5 begins.
