# G3.29 — Notification Provider Activation Contract

## Objective

Define the bounded, deny-by-default activation boundary for future notification providers while keeping all real external delivery disabled.

## Required behavior

- preserve `UnconfiguredNotificationProviderRegistry` as the production-safe default;
- explicit channel-scoped provider activation only;
- reject unsupported provider keys, unsupported channels, conflicting declarations, and incomplete configuration;
- keep provider credentials/secrets exclusively in the approved runtime secret/config boundary;
- never persist or log credentials, destination tokens, raw provider responses, or vendor error payloads;
- preserve the existing provider-neutral `NotificationProviderAdapter` contract and stable delivery idempotency key;
- define bounded provider error normalization and provider-reference handling;
- keep provider activation/readiness separate from PostgreSQL readiness and ordinary application health;
- prove default-off behavior and channel isolation with tests;
- add no vendor SDK, credentials, endpoint, network call, or real delivery.

## Required tests

- no configuration keeps every channel fail closed with `PROVIDER_UNAVAILABLE`;
- configuring one channel does not activate another channel;
- invalid or incomplete activation configuration fails closed;
- secret values cannot appear in returned config state, logs, queue payloads, attempt evidence, or thrown public errors;
- adapter failures cross the worker boundary only as bounded error codes;
- existing notification worker idempotency/retry behavior remains unchanged;
- ordinary unit tests remain parallel and infrastructure tests retain the accepted deterministic execution policy.

## Explicit exclusions

No Twilio, WhatsApp, SMS, email, push, or other real vendor integration; no provider account creation; no credentials; no outbound network calls; no webhook handling; no inbound delivery receipts; no production deployment; no Maps, FHIR, ABDM, billing, returns, recall, quarantine release, or approval for real healthcare data.

## Acceptance criteria

Task is complete only after implementation review, exact-head dependency audit, migration/drift and populated-upgrade verification where applicable, formatting, lint, PostgreSQL/Redis-backed tests, build, security/privacy review, merge, and governance synchronization. Until then ADR-021 and G3.29 remain proposed.
