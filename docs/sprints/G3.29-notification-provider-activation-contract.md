# G3.29 — Notification Provider Activation Contract

## Objective

Define the bounded, deny-by-default activation boundary for future notification providers while keeping all real external delivery disabled.

## Selected first channel

`EMAIL` is the only channel approved by this contract for a future first provider adapter. SMS, WhatsApp, push, and all other channels remain unsupported and fail closed.

## Required behavior

- preserve `UnconfiguredNotificationProviderRegistry` as the production default in this sprint;
- explicit channel-scoped provider activation only;
- reject unsupported provider keys, unsupported channels, conflicting declarations, missing/malformed credential references, and incomplete configuration;
- keep credential values exclusively in the approved injected runtime secret/config boundary; store only bounded credential references/names in activation configuration;
- never persist or log credentials, destination tokens/addresses, composed message bodies, raw provider responses, or vendor error payloads;
- preserve the provider-neutral `NotificationProviderAdapter` boundary and the notification delivery ID as the logical idempotency key;
- normalize acknowledgements to `ACCEPTED`, `REJECTED`, or `UNKNOWN`;
- normalize provider failures to coded `TRANSIENT` or `TERMINAL` classifications;
- enforce a bounded provider network timeout contract of 250 ms through 10 s, defaulting to 5 s;
- require exact provider-key/channel matching and prohibit silent fallback;
- keep tenant authority entirely inside MedSphere; provider data cannot establish or widen tenant authority;
- expose metadata-only provider capability state as `DISABLED`, `READY`, `DEGRADED`, or `UNAVAILABLE`;
- keep provider activation/readiness separate from PostgreSQL readiness and do not perform provider network probes in this sprint;
- prove default-off behavior, channel isolation, exact adapter matching, bounded configuration, and secret-safe views with tests;
- add no vendor SDK, credentials, endpoint, network call, or real delivery.

## Deliverables

- ADR-021;
- this sprint contract;
- `notification-provider-activation.contracts.ts` with typed activation/config/result/error/readiness contracts and exact-match fail-closed registry;
- `notification-provider-activation.contracts.spec.ts` unit/contract coverage;
- `docs/security/G3.29-notification-provider-threat-failure-model.md`;
- exact-head CI evidence and post-merge governance synchronization.

## Required tests

- no activation keeps EMAIL fail closed with `PROVIDER_UNAVAILABLE`;
- unsupported channels fail closed and never fall back;
- invalid or incomplete activation configuration fails closed;
- disabled configuration cannot contain conflicting provider/credential activation fields;
- timeout limits are bounded;
- secret references do not appear in returned safe config state;
- configured provider key must exactly match the supplied adapter;
- provider failures expose only bounded internal error metadata;
- existing notification worker idempotency/retry behavior remains unchanged;
- ordinary unit tests remain parallel and infrastructure tests retain the accepted deterministic execution policy.

## Explicit exclusions

No real vendor integration; no provider account creation; no credential value; no outbound network call; no webhook handling; no inbound delivery receipt; no production deployment; no real-healthcare-data approval; no Maps, FHIR, ABDM, billing, returns, recall, Blood Bank, analytics expansion, or unrelated frontend work.
