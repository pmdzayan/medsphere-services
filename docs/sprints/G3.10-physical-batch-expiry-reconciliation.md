## Objective

Implement ADR-011 as one bounded, non-HTTP worker that marks due physical
batches `EXPIRED`, atomically expires reservations holding those batches, and
records immutable tenant-system evidence without pretending the stock was
physically disposed.

## Functional requirements

### Worker boundary

- Add one standalone one-shot application-context worker inside the accepted
  Inventory composition in `auth-service`.
- Do not open an HTTP listener or add a route, controller, permission, browser
  API, gateway route, scheduler service, queue, or dependency.
- Capture one authoritative database `asOf` timestamp per run.
- Select undeleted `ACTIVE` batches with `expiryDate <= asOf` in stable
  `expiryDate`, `tenantId`, `id` order.
- Enforce documented positive safe-integer batch-size and maximum-record
  defaults and hard limits.
- Enforce documented hard limits for affected reservations and allocations per
  candidate; fail the candidate closed before mutation when either limit is
  exceeded.
- Attempt each selected ID at most once per run.

### Per-batch transaction

Process each candidate in one accepted serializable transaction with bounded
retry:

1. Re-read the exact database-derived scope, state, quantities, version, and
   due date.
2. Safely skip a candidate that is missing, deleted, no longer active, or no
   longer due.
3. Load distinct active reservations with `HELD` allocations on the candidate,
   ordered stably.
4. Validate every affected reservation's complete item/allocation totals and
   require every active allocation to remain `HELD`.
5. Release all allocations for each affected reservation using the accepted
   shared transaction client and allocation-release primitive.
6. Transition each affected reservation to `EXPIRED`, set the same `asOf`,
   increment version, append one deterministic `EXPIRE` command, and append one
   `inventory.reservation.expired` tenant-system audit with batch-expiry cause.
7. Prove the candidate held quantity is zero after releases.
8. Preserve `receivedQuantity` and `onHandQuantity`; set only status to
   `EXPIRED` and increment version once.
9. Insert one immutable expiry record and one `inventory.batch.expired`
   tenant-system audit using the same `asOf`.

No stock movement is permitted because on-hand quantity is unchanged.

### Run result and failure behavior

- Return bounded counts: selected, reconciled, skipped, failed, affected
  reservations, and released units, plus allowlisted failure categories.
- Continue attempting other selected batches after one candidate failure.
- Exit non-zero after the bounded run when any selected candidate fails.
- Never swallow or relabel a rollback, invariant, concurrency, command, record,
  or audit failure as success.

## Database and migration requirements

Add one forward migration defining an immutable `BatchExpiryRecord` with:

- UUID primary key;
- tenant, inventory, provider, product, and batch identifiers;
- exact expiry date;
- non-negative on-hand quantity at reconciliation;
- positive resulting batch version;
- database reconciliation and creation timestamps;
- one record per batch;
- composite same-tenant/inventory/provider/product/batch foreign keys;
- query-driven indexes; and
- an update/delete rejection trigger.

Add a stable due-batch selection index appropriate to the actual query. Extend
the database audit-event allowlist for `inventory.batch.expired`. If reservation
audit metadata adds a cause, constrain it to the exact accepted value. Do not
weaken legacy constraints or reinterpret existing `EXPIRED` movements.

Update Prisma relations and the populated-upgrade verifier. Prove a clean
deployment, no drift, valid populated G3.9 upgrade, preservation of existing
data, and fail-closed invalid expiry-record/audit rows.

## Concurrency and idempotency requirements

- Two workers selecting the same batch produce one reconciliation.
- Repeated execution cannot release a reservation, transition a batch, insert a
  command/record, or append an audit twice.
- G3.7 expiry and staff cancel/complete races have one valid terminal winner.
- A reservation allocated across two due batches expires once and releases all
  of its allocations once.
- Exact conditional writes include tenant scope, IDs, status, quantities, due
  date where supported, and version.
- Arithmetic uses safe integers and never clamps negative or overflow values.

## Security and privacy

- Tenant and provider scope come only from selected database rows.
- No client, browser, header, token, membership, role, permission, user, or
  actor identity is accepted.
- Use tenant-system audit with no user actor fields.
- Logs and summaries contain bounded counts and categories only.
- Never expose or log subject-user IDs, patient identity, prescription or
  clinical data, reservation notes, contact data, credentials, tokens, prices,
  request bodies, or free text.

## Explicitly out of scope

- physical removal, write-off, disposal, destruction, reversal, or evidence
  attachments;
- quarantine, recall, supplier return/refund, approval, or controlled medicine;
- expiry alerts, notifications, event outbox, analytics, reports, or frontend;
- patient/public reservation creation or partial reservation fulfilment;
- HTTP, BFF, gateway, permission, authentication, or provider-assignment
  changes;
- production scheduling, deployment, observability, or release approval.

## Testing requirements

Add focused unit and real PostgreSQL tests proving:

1. authoritative database time, bounded stable selection, and hard limits;
2. per-candidate reservation/allocation limits fail closed without mutation;
3. future, deleted, already expired, and concurrently changed batches skip;
4. unheld due batch status transition preserves received/on-hand quantities;
5. single- and multi-reservation holds are fully released;
6. multi-item and multi-batch reservations expire atomically;
7. reservation and batch versions, commands, records, and audit timestamps are
   exact;
8. no stock movement is created;
9. repeat and overlapping worker execution is idempotent;
10. races with G3.7, cancel, complete, and another batch candidate have one
    valid winner;
11. malformed totals, non-held allocations, underflow, overflow, stale writes,
    record conflicts, and audit failures roll back the complete candidate;
12. one failure does not hide successful independent candidates and causes a
    non-zero worker exit;
13. expiry records and audit metadata reject cross-tenant, mutable, malformed,
    sensitive, or unexpected values;
14. clean migration, populated upgrade, and drift gates pass; and
15. no route, permission, browser identity, dependency, or second owner is
    introduced.

Do not weaken, delete, skip, or replace existing tests.
